新入网（在网 0 个月）的客户，系统把累计消费写成了一个空格 " "。只要一列里有一个值不是数字，pandas 就只能把整列当文本。这是真实业务数据里非常常见的坑。

STEP 2

数据清洗：只做"规则型"清洗

为什么

清洗分两类，界限一定要清楚：

  • 规则型：不需要从数据里"学"任何参数，比如去重、统一写法、把空格转成 0。它对每一行的处理结果和其他行无关，所以可以在切分前做，上线时对新数据原样复用。
  • 学习型：需要从数据里算出一个数，比如用中位数填缺失、标准化。这个数如果用全部数据算，测试集的信息就漏进了训练。所以必须在切分后、放进 Pipeline（第 4 步）。

所以下面 clean() 里年龄异常值只是改成缺失，填多少留给 Pipeline 里的 SimpleImputer。

常见坑

  • 用 df.dropna() 一删了之：本例中缺失的使用时长是埋点问题，与流失无关，删掉会白白损失样本。
  • 空格、"N/A"、"-"、"null" 都可能代表缺失，isna() 统计不到它们。
  • ID 列不是特征。模型可能记住 ID 的规律（比如新用户 ID 更大），上线时完全不成立。

统一写法是规则型操作，处理一行时不需要看其他行。中位数和标准化都要从数据中"学"参数，必须只在训练集上学。

STEP 3

数据切分：把测试集锁进保险柜

为什么

测试集扮演的是"上线后遇到的新客户"。它的唯一用途，是在所有决定都做完之后，给出一次诚实的成绩。所以它必须尽早切出来，并且封存：之后的特征处理、选模型、调参，都只能看训练集。

为什么要 stratify=y？我们不加分层、换 30 个随机种子各切一次，测试集的流失率在 到 之间晃动。少数类越少，这种晃动越大，评估结果也跟着不稳。

测试集最重要的使用规则是什么？

每看一次测试集，你的决定就会被它影响一点，它就不再是"没见过的数据"了。第 6 步会用实验证明：反复看测试集会让汇报的分数系统性虚高。

STEP 4

特征与预处理：所有"学习型"处理都进 Pipeline

为什么

数值列和类别列需要不同的处理：数值要填缺失、标准化；类别要独热编码。ColumnTransformer 把它们分开处理再拼起来，Pipeline 再把预处理和模型串成一个整体。

串起来的好处不只是代码整洁。Pipeline.fit 保证预处理只在训练数据上学习；交叉验证时，每一折也只用该折的训练部分去学。这是 scikit-learn 官方推荐的防泄漏方式。

    为什么要把 StandardScaler 放进 Pipeline，而不是事先对整个 X 做 fit_transform？

    事先在整个 X 上 fit，测试集的均值方差就参与了训练数据的变换。标准化造成的泄漏通常不大，但特征选择、目标编码这类处理造成的泄漏可以大到离谱，就像上面的随机数实验。养成习惯：凡是 fit，都进 Pipeline。

    STEP 5

    建模：先立一个"傻瓜基线"，再上真模型

    先猜一猜：一个什么都不学、永远回答"不流失"的模型，准确率是多少？

    真实结果：

    流失客户只占约两成，所以闭着眼睛说"都不会走"，就能拿到八成的准确率。但它一个要走的客户都找不出来（召回率 = 0）。这就是不平衡数据下的准确率陷阱。

    为什么

    DummyClassifier 是一把尺子：任何模型都必须先明显超过它，才算学到了东西。下面四个模型都用 5 折交叉验证、只在训练集上比较。AUC 衡量的是排序能力：随机挑一个流失客户和一个留存客户，模型给前者打分更高的概率。0.5 等于瞎猜，1 是完美。

    模型擂台

    5 折交叉验证结果（训练集）

    看 Dummy 那一行：准确率不低，召回率和 AUC 却是 0 和 0.5。再看逻辑回归：最简单的模型，AUC 却是最高的之一。

    不平衡怎么办

    class_weight="balanced" 的效果

    加权后模型更"敢"把客户判成流失：召回率大涨，精确率下降。它的效果相当于把判定阈值调低，所以第 7 步我们直接用业务利润来选阈值。

    一个模型准确率 85%，而 Dummy 基线准确率是 。这说明什么？

    在不平衡数据上，准确率的"及格线"是多数类占比，而不是 50%。判断模型好坏要看它比基线强多少，并结合召回率、AUC 这类不被多数类主导的指标。

    漏点 4 · 反复看测试集

    挑出来的"冠军"，汇报的分数为什么总是偏高？

    假设团队试了 50 个版本，每次都拿同一份 200 人的小测试集打分，最后挑最高的去汇报。测试集参与了"挑选"，它就变成了训练过程的一部分。我们把"抽小测试集 → 挑冠军 → 看冠军在其余新客户上的真实分"重复了 200 次：

    有 的情况下，汇报分比真实分高。平均高估 AUC。原因是 50 个版本里，总有几个"碰巧"适合这 200 个人，挑最高的就等于挑中了运气。

    我们的做法：选型和调参全部用训练集上的交叉验证完成，测试集直到第 7 步才打开一次。这样测试集上的分数，才是对上线表现的无偏估计。如果确实需要反复比较，就再切一份"验证集"给它用，测试集依然不动。

    两个模型交叉验证 AUC 只差 0.001，该怎么选？

    0.001 远小于交叉验证本身的波动，统计上就是打平。打平时，简单性、可解释性、上线成本才是决定因素。第三个选项正是刚刚演示的泄漏。

    漏点 5 · 训练与线上不一致

    线下一套口径，线上一套口径

    • 线上工程师用 Java 重写了清洗逻辑，"累计消费"的空格被当成缺失，而训练时是 0。
    • 训练用的"近 30 天"截止到月底，线上截止到月初，口径差了一周。
    • 只保存了模型，标准化参数线上重新算了一遍。
    • 新数据走同一个 clean() 函数。
    • 用 joblib 保存整条 Pipeline（预处理参数和模型在一起），原始列进、概率出。官方文档也介绍了更安全的 skops 格式。
    • 每个特征写清"数据来源 + 计算截止时间"，上线前逐一核对；上线后每月监控 AUC 和预测分布，季度重训。

    挽留电话成本从 80 元涨到 300 元，最合理的做法是？

    模型负责估计"谁可能走"，阈值负责"值不值得打"。成本变了，排序能力没变，只需要重新选阈值。去上面的利润实验台把成本改成 300 试试。

    复盘清单
    • 业务问题 → 二分类；成功标准 → 利润，不是准确率。
    • "挽留专员通话次数"是目标泄漏：预测时点之后才产生。
    • 规则型清洗可以先做；学习型处理全部进 Pipeline。
    • 先立 Dummy 基线；不平衡数据看召回率、AUC、PR 曲线。
    • 选型调参靠交叉验证，测试集只开一次。
    • 阈值是业务参数；保存整条 Pipeline；上线后监控与重训。
